# Измеренное: глава 4

PostgreSQL 16.15, контейнер, `shared_buffers = 256MB`, 8 ядер.
Данные: 5 млн заказов и 500 тыс. клиентов, 748 МБ + 51 МБ.
Запрос: хеш-соединение, хеш-агрегация, сортировка.

## Пиковая память ведущего процесса (`VmHWM`)

| `work_mem` | с параллелизмом | без параллелизма |
|---|---|---|
| 4 МБ | 216 МБ | 368 МБ |
| 64 МБ | 399 МБ | 399 МБ |
| 256 МБ | 465 МБ | 417 МБ |

Обратите внимание на первую строку: **без воркеров ведущий процесс
занял больше**, чем с ними. Работа никуда не делась — при параллельном
плане её часть унесли отдельные процессы со своей памятью, которой в
этой таблице нет вообще.

## Что на самом деле заняла одна выполняющаяся команда

`EXPLAIN (ANALYZE)` того же запроса при `work_mem = 256MB`:

```
Sort Method: quicksort  Memory: 236309kB
Worker 0:  Sort Method: quicksort  Memory: 237718kB
Worker 1:  Sort Method: quicksort  Memory: 236633kB
Buckets: 524288  Batches: 1  Memory Usage: 30752kB
```

Три сортировки по 236 МБ плюс хеш-таблица 30 МБ — около **740 МБ на
один запрос** при `work_mem = 256MB`. Множитель почти ровно три, и
получен он не из рассуждения, а из плана.

## Предохранитель

Тот же запрос при `work_mem = 4MB`:

```
Sort Method: external merge  Disk: 170400kB
Worker 0:  Sort Method: external merge  Disk: 171008kB
Worker 1:  Sort Method: external merge  Disk: 169528kB
Buckets: 262144  Batches: 4  Memory Usage: 8736kB
```

Каждый процесс сбросил на диск примерно по 170 МБ, хеш разбился на
четыре порции — и запрос **отработал**. Это раздел 4.7 в чистом виде:
маленький `work_mem` даёт медленно, но живо.
