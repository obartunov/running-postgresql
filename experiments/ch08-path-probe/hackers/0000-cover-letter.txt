Subject: [PATCH v3 0/2] planner: add injection points for path pruning

EXPLAIN shows the plan that survived planning.  It does not show what
happened to the other candidates, and that is the question people actually
have when an index exists, looks applicable, and does not appear in the
plan.

There are three boundaries in pathnode.c where candidates disappear:

  * add_path_precheck() can reject a candidate before a Path exists;
  * add_path() can reject a newly built Path;
  * add_path() can remove an older Path that had survived until then.

This series adds injection points at those boundaries, plus one at
acceptance, and a small action in the existing injection_points test module
that prints the relevant planner properties as one NOTICE line.

  0001  planner: add injection points for path pruning
  0002  injection_points: add planner path-prune notice action

Why the accept event is included
--------------------------------

The motivating question is not "was this path discarded" but "was it
discarded early, or did it survive and lose later".  Those two situations
call for completely different actions, and the deaths alone cannot tell
them apart: a path that survived produces no event at all.

Concretely, one physical index produces two different candidates, and on
the demo data set the trace shows both:

  event=accept   rel={2} new_type=IndexScan new_index=32826
                 new_required_outer={}
  event=accept   rel={2} new_type=IndexScan new_index=32826
                 new_required_outer={1}
  event=displace rel={2} new_type=BitmapHeapScan new_index=32826
                 new_required_outer={1}
                 old_type=IndexScan old_index=32826
                 old_required_outer={1}

The unparameterized path over that index and the parameterized one are not
the same planner candidate, and the displacement happens between two paths
over the same physical index.  Without the accept event only the third line
exists, and the first two facts are unobservable.

The second demo query is the case that motivates the series: a wider outer
relation, and an index that does not appear in the final plan at all.

  Hash Join  (cost=210.28..31730.39 rows=497216)
    ->  Seq Scan on pp_orders o  (cost=0.00..28894.00 rows=1000000)
    ->  Hash -> Index Only Scan using pp_customers_pkey on pp_customers c

The trace for that query, abridged:

  event=accept   rel={2}   new_type=IndexScan new_index=32826
                 new_total=86426.48 new_rows=1000000 new_required_outer={}
  event=accept   rel={2}   new_type=IndexScan new_index=32826
                 new_total=16.19    new_rows=99      new_required_outer={1}
  event=accept   rel={1,2} new_type=NestLoop  new_total=56961.08
  event=displace rel={1,2} new_type=HashJoin  new_total=31730.39
                 old_type=NestLoop

The row estimates make the point on their own: 1000000 against 99 over the
same index oid.  Both candidates are accepted, including the parameterized
one; the Nested Loop built on top of it is accepted as well and is then
displaced by a cheaper Hash Join.  The index was not pruned - the join
method above it lost.  That distinction is the whole point, and it is not
derivable from EXPLAIN.

Event counts on the first demo query, which are themselves informative:

  accept          16
  precheck-reject 16
  reject           3
  displace         3

Half of the pruning happens in add_path_precheck(), before any Path is
built.  That is hard to learn any other way and is the reason the precheck
boundary is included.

Lifetimes
---------

Every point fires while the path it describes is still live: displace fires
before the list cell is deleted and before pfree(); reject fires before
new_path is freed after the loop.  No callback can observe a freed Path.

The precheck payload has no new Path pointer, because at that boundary no
Path has been built.  It carries the proposed costs, disabled_nodes,
pathkeys and required_outer instead.  That asymmetry is a property of the
planner boundary, not of the instrumentation.

Overhead
--------

The payload structs and their construction exist only under
USE_INJECTION_POINTS, so ordinary builds are unchanged.

For builds that do have injection points enabled, the four points are
loaded once per planner invocation and consulted through the process-local
cache, rather than looked up in shared memory on every add_path() call.

I measured that choice rather than assuming it.  On a six-way join planned
in a loop, with nothing attached, with and without the cached form:

  cached form:  9654, 9746, 10047 plans/s
  plain form:   9305, 9574,  9789 plans/s

The medians differ by under 2%, and the spread within each variant is
larger than the difference.  On this machine and this query the benefit is
not demonstrated.  The cached form is kept on design grounds - it avoids a
shared memory lookup in a function called this often - and not because a
speedup was measured.  A better measurement on a machine that is not a
single-core container would be welcome.

The load is done in planner(), before planner_hook is consulted.  Doing it
in standard_planner() would mean that a hook replacing the planner entirely
leaves the cache empty and the points silently produce nothing, which is
the worst possible failure mode for diagnostic instrumentation.

Relationship to pg_plan_advice
------------------------------

pg_plan_advice answers "can the planner produce this plan shape if its
choices are constrained".  These injection points answer a different
question: "what happened to the candidates during the normal planning run".
A successful advice does not show that the corresponding path survived the
unconstrained run, because advice itself changes the search.  The two are
complementary, and neither substitutes for the other.

Style
-----

pgindent (with pg_bsd_indent built from src/tools) makes no changes to the
four touched files; the TAP test is pgperltidy-clean; the two new typedefs
are added to typedefs.list.

Testing
-------

0002 includes a TAP test that asserts structural facts only: that accept
and pruning events can be observed, that a parameterized candidate is
reported with a non-empty required_outer, and that an index path is
reported with its index oid.  It does not compare the output as a whole,
because the lines carry costs and row estimates that are not stable across
platforms or planner changes, and this series should not turn particular
costs into expectations.

What is deliberately not here
-----------------------------

Partial paths.  add_partial_path() and add_partial_path_precheck() have
analogous pruning and no points.  The demo turns parallelism off, so the
series does not need them; they should be added when a concrete test does.

Open questions
--------------

  * Is optimizer/pathnode.h an acceptable home for these test-only payload
    structs, guarded by USE_INJECTION_POINTS?
  * Is planner() the right place to load the points?  It is correct with
    respect to planner_hook, but it costs four cache lookups per planner
    invocation even when nothing is attached.
  * Are four boundaries the right set, or should accept be dropped in
    favour of a smaller series?
  * Should the names be shorter, e.g. planner-path-precheck-reject?

Demo
----

The attached demo is SQL plus a POSIX shell script, with no Python
dependency, and it does not assert a final plan.  demo/trace-observed.log
is the trace produced by the run described above, for reference.
