# Эксперимент к главе 8: обе стороны сделки

```sh
createdb part_bench
export PGDATABASE=part_bench
psql -f setup.sql      # год данных, 3 млн строк, обе таблицы
```

`setup.sql` создаёт одинаковое содержимое в двух видах: обычная
таблица `events_plain` и `events_part`, разбитая по месяцам.

## 1. Что вы покупаете

```sh
./removal.sh
```

Удаляет один и тот же месяц двумя способами и печатает четыре
величины для каждого: время, объём WAL, размер таблицы после,
работу, оставшуюся для VACUUM.

Ожидание — разница в порядки. Проверьте на своих данных: при коротких
строках и одном индексе `DELETE` может оказаться терпимым, и тогда
одна из двух причин разбивать таблицу отпадает.

Обратите внимание на последний шаг: после `VACUUM` размер обычной
таблицы почти не уменьшается. Место освобождено внутрь таблицы, а не
отдано системе — это раздел 2.7. У секционированной оно вернулось в
момент `DROP`.

## 2. Чем вы платите

```sh
./pruning.sh
```

Создаёт пустые таблицы на 12, 365 и 1095 секций и меряет время
планирования одного простого запроса — с ключом секционирования в
условии и без.

Секции пустые намеренно: измеряется планирование, а не выполнение.
С ключом время почти не зависит от числа секций. Без ключа растёт, и
это цена каждого запроса, не попавшего в отсечение.

В конце скрипт подсказывает, как посмотреть число блокировок такого
запроса. Запрос без отсечения берёт блокировку на каждую секцию — это
прямая связь с ограничениями из главы 6.

## Что стоит попробовать сверх сценариев

**Ловушка со статистикой родителя.** После загрузки данных выполните:

```sql
SELECT relname, last_analyze, last_autoanalyze
FROM pg_stat_all_tables WHERE relname LIKE 'events_part%';
```

У секций автоанализ отработает, у родителя `last_autoanalyze` останется
пустым навсегда. Это раздел 8.4.

**Секция по умолчанию.** Создайте `DEFAULT`-секцию, вставьте в неё
строки за будущий месяц, затем попробуйте присоединить настоящую секцию
на этот месяц. `ATTACH` прочитает `DEFAULT` целиком и, найдя
конфликтующие строки, откажется. Это раздел 8.2.
