# Эксперимент к главе 1: сколько стоит частый чекпойнт

Воспроизводится на одной машине или VM. Спецжелезо не нужно.

## Что доказывает

Что при одной и той же нагрузке частые чекпойнты генерируют кратно
больше WAL, и что почти вся разница — full-page images, а не запись
данных.

## Порядок

```sh
. ./env.sh
./setup.sh                 # один раз
```

Для каждого прогона: применить конфиг, перезапустить сервер, прогнать.

```sh
cat conf/A-tight.conf >> $PGDATA/postgresql.conf   # или через ALTER SYSTEM
pg_ctl restart -D $PGDATA
./run.sh A
```

Затем то же для `B-wide.conf` и (только на выбрасываемом инстансе)
`C-nofpi.conf`. Между прогонами возвращайте конфиг в исходное
состояние, иначе параметры наложатся.

## Разбор

```sh
python3 analyze.py results/A/pgbench 10 > results/A/p99_by_window.tsv
grep checkpoint /path/to/postgresql.log > results/A/checkpoints.log
```

Три числа на прогон:

1. **WAL на транзакцию** — `pg_wal_lsn_diff` между `before.txt` и
   `after.txt`, делённое на прирост `xacts`.
2. **Доля чекпойнтов по объёму** — прирост `num_requested` против
   прироста `num_timed`.
3. **Амплификация задержки** — p99/p50 из stderr `analyze.py`.

Наложите `p99_by_window.tsv` на моменты `checkpoint starting` из
`checkpoints.log`. Зубец должен садиться на начало окна (FPI) или на
конец (фаза sync) — это разные диагнозы.

## Прогон C

`full_page_writes = off` снимает защиту от неполной записи страницы.
Прогон существует ради одного числа: какая доля WAL является full-page
images. Выполняется только на инстансе, который не жалко потерять, и
никогда не превращается в рекомендацию для production.

## Что фиксировать в результатах

`version.txt`, `settings.txt`, `host.txt` пишутся автоматически. К ним
руками добавьте: модель диска, файловую систему и параметры монтирования,
был ли на машине посторонний ввод/вывод во время прогона. Без этого
цифры нельзя сравнивать между стендами.
