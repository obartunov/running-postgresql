Subject: [PATCH 0/2] planner: injection points for path pruning

EXPLAIN answers "which plan won". It does not answer "what happened to the
candidates on the way", and that second question is the one a DBA actually
asks when an index is present, looks applicable, and does not appear in the
plan.

Motivating case, two ordinary tables:

  CREATE TABLE customers (id bigint PRIMARY KEY, segment int);
  CREATE TABLE orders (id bigint PRIMARY KEY,
                       customer_id bigint NOT NULL,
                       amount numeric);
  CREATE INDEX orders_customer_idx ON orders (customer_id);

  -- 20k customers, 2M orders

  SELECT o.* FROM customers c JOIN orders o ON o.customer_id = c.id
   WHERE c.id BETWEEN 100 AND 4999;

Observed plan:

  Hash Join
    ->  Seq Scan on orders o
    ->  Hash -> Index Only Scan using customers_pkey on customers c

Question from the field: why was orders_customer_idx not used?

What is available today:

  EXPLAIN            shows only the winner
  pg_plan_advice     can show that a Nested Loop with a parameterized
                     Index Scan is a viable constrained alternative

Neither shows what happened during the normal planning run. In particular
they cannot distinguish two very different situations:

  (a) the parameterized index path was created, survived add_path(), and
      the Nested Loop above it lost to a cheaper Hash Join;

  (b) the parameterized index path was pruned locally, so the Nested Loop
      that would have used it could not be built at all.

From the outside both look like "the planner does not like this index",
and they call for completely different actions.

This series adds injection points that make the difference observable.

  0001  planner: add injection points for path pruning
  0002  injection_points: add a callback for planner path pruning

With an --enable-injection-points build, the motivating query above
produces (abridged, from a run on this series):

  NOTICE: path-pruning-reject:   rel {2} node 351 pathkeys 0 req_outer {1}
  NOTICE: path-pruning-displace: rel {1 2} node 365 pathkeys 0 req_outer {}
  NOTICE: path-pruning-reject:   rel {1 2} node 363 pathkeys 0 req_outer {}

which shows that in this case the answer is (a): the join level decision,
not the scan level one, is what removed the index from the plan.

Notes for review.

The payload is a typed struct rather than a string. The existing "notice"
callback in the injection_points test module assumes the argument is a
printable string, so attaching it to these points prints garbage; 0002 adds
a callback that understands the payload. If the project prefers injection
point arguments to stay strings, 0001 can pass NULL and expose only the
structural events, at the cost of losing required_outer, which is exactly
the field that distinguishes the two situations above.

Building PathPruningInfo happens only under USE_INJECTION_POINTS, so
ordinary builds see no change in add_path(). Whether even that is
acceptable in such a hot function is a question for reviewers; an
IS_INJECTION_POINT_ATTACHED() guard is possible if the struct construction
is considered too expensive.

No regression test is proposed that depends on specific costs: the same
query can legitimately produce different pruning decisions after a planner
or cost model change. A demo script is included in the thread instead, and
what it checks are structural facts - that reject and displace events occur,
and that a parameterized path is reported with a non-empty required_outer.
