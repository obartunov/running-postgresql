# Эксперимент к главе 6: где предел полезной одновременности

Две части. Первая ищет точку перегиба, вторая показывает ёмкость,
съеденную удержанием.

```sh
createdb conn_bench
export PGDATABASE=conn_bench
./setup.sh
```

Масштаб взят небольшой намеренно: данные должны помещаться в
`shared_buffers`. Иначе кривая упрётся в диск, и вы измерите главу 1,
а не эту.

## 1. Кривая

```sh
./sweep.sh          # только чтение
./sweep.sh write    # с записью
```

Девять шагов по минуте - около десяти минут на прогон. Результат в
`results/*/sweep.tsv`: клиенты, tps, средняя задержка, p99.

Подключение идёт **напрямую к PostgreSQL, без пулера**: измеряется
предел базы, а не настройка пула. Размер пула выводится из этого
предела, а не наоборот.

Что искать:

- точка, где `tps` перестаёт расти, - предел полезной одновременности;
- после неё задержка растёт примерно линейно по числу клиентов: всё
  добавленное уходит в ожидание;
- если `tps` начинает падать - вы за плато, и система тратит часть сил
  на само наличие соперничества.

Два числа для отчёта: во сколько раз оптимум меньше вашего
`max_connections`, и сколько задержки добавилось в точке, где
пропускная способность уже не росла. Второе - цена очереди, стоящей не
на своём месте.

`p99` считается скриптом из главы 1
(`../ch01-checkpoint/analyze.py`); если его нет, колонка останется
пустой, а `tps` и средняя задержка всё равно наберутся.

## 2. Ёмкость, съеденная удержанием

```sh
./starvation.sh 10
```

Открывает десять транзакций, каждая сделала один `SELECT` и ушла
думать, и печатает состояние базы: сессии заняты, активных запросов
нет.

При прямом подключении это съеденные `max_connections`. Если у вас
поднят PgBouncer в режиме транзакций, запустите то же самое через него
и посмотрите `SHOW POOLS`: `cl_waiting` растёт при простаивающей базе.
Это ровно тот диагноз, о котором глава: ёмкость съедена не работой, а
удержанием.

Скрипт закрывает свои транзакции сам, при выходе тоже. Если прервали
жёстко - проверьте:

```sql
SELECT pid, application_name, state FROM pg_stat_activity
WHERE application_name LIKE 'holder-%';
```

## Оговорка

Обе части измеряют вашу машину, а не PostgreSQL вообще. Число ядер,
диск, версия сервера и форма нагрузки меняют точку перегиба в разы.
Смысл стенда - получить своё число и перестать спорить о чужих.
