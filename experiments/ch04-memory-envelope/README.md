# Эксперимент к главе 4: измерьте свой множитель

Числа в главе - иллюстрация арифметики. Ваш множитель между `work_mem`
и реально занятой памятью зависит от планов вашей нагрузки, и получить
его можно только измерением.

## Требования

PostgreSQL работает **на этой же машине**: скрипт читает
`/proc/<pid>/status`. В managed-окружении так измерить не выйдет -
там остаётся `EXPLAIN (ANALYZE)` и `log_temp_files`.

```sh
createdb mem_bench
export PGDATABASE=mem_bench
psql -f setup.sql          # ~5 млн строк, около 2 ГБ
```

## Три вещи, которые делает стенд

### 1. Сколько узлов претендует на бюджет

```sh
./explain.sh 64MB
```

Считает потребителей в плане и показывает, кто сбросился на диск
(`Batches: > 1`, `Sort Method: external merge`). Это переводит
`work_mem` из настройки в число.

### 2. Пиковая память при разных `work_mem`

```sh
./peakmem.sh            # как настроен сервер
./peakmem.sh serial     # без параллельных воркеров
```

Результат - `results/*/peak.tsv`. Множитель считается по крайним
точкам: `ΔVmHWM / Δwork_mem`.

Разница между `parallel` и `serial` показывает вклад воркеров в память
лидера. Полная память запроса больше: у каждого воркера свой процесс со
своим `VmHWM`, и суммировать надо по всем процессам запроса.

**Множитель около единицы - нормальный результат**, а не неудача. Он
означает, что в плане доминирует один узел, и считать вам проще, чем
описано в главе.

### 3. Где начинается плохой отказ

**Только в контейнере или виртуалке с заданным лимитом памяти, которую
не жалко.** Не на машине, где живёт что-то нужное.

```sh
# пример: cgroup v2 с лимитом 2 ГБ на весь кластер
systemd-run --scope -p MemoryMax=2G --user pg_ctl -D "$PGDATA" start

# затем наращивать одновременность
for n in 2 4 8 16 32; do
  seq $n | xargs -P "$n" -I{} psql -X -q -c "SET work_mem='64MB'; $(cat query.sql)"
done
```

Смысл не в том, чтобы получить число, а в том, чтобы увидеть **форму**:
до последнего шага всё выглядит нормально, а потом падает разом всё.
В логе появится `terminated by signal 9` и `reinitializing` - падает не
запрос, а кластер.

Перед прогоном включите `log_temp_files = 0`: тогда в логе останется
видно, какие запросы успевали сбрасываться на диск (хороший отказ) до
того, как наступил плохой.

## Замените запрос

`query.sql` - синтетический отчёт с хеш-соединением, хеш-агрегацией и
сортировкой. Подставьте свой реальный тяжёлый запрос: смысл стенда в
вашем множителе, а не в этом примере.
