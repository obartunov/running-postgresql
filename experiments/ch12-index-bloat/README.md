# Эксперимент к главе 12: измерение против оценки

```sh
createdb bloat_bench
export PGDATABASE=bloat_bench
```

Нужен `pgstattuple` из `contrib`. Скрипт установит расширение сам.

## 1. Как выглядит раздувание

```sh
./bloat.sh
```

Собирает таблицу с индексом по обновляемой колонке, гоняет несколько
раундов обновлений с `VACUUM` между ними и печатает три замера
`pgstatindex`: после сборки, после нагрузки и после
`REINDEX CONCURRENTLY`.

Смотреть на `leaf_density_pct`. Свежесобранный B-tree даёт около 90 %,
раздутый — 50–60 %. Это **измерение**: функция прочитала индекс
целиком.

Рядом печатается наивная оценка. Сравните её и с измерением, и с тем
оценочным запросом про bloat, который используется у вас в проде.
Расхождение — это и есть содержание раздела 12.2.

Автовакуум на таблице отключён намеренно, чтобы моменты очистки
задавались скриптом. В проде так делать нельзя.

## 2. Во что обходится лишний индекс

```sh
./index-cost.sh
```

Одна и та же нагрузка обновлений на четырёх вариантах таблицы: без
индексов, с индексом по неизменяемой колонке, с индексом по
обновляемой, с четырьмя индексами. Печатает байты WAL на обновлённую
строку и долю HOT-обновлений.

Ожидаемая форма: переход от второго случая к третьему — скачок, а не
приращение. Индекс по обновляемой колонке отключает HOT для таблицы
целиком, и дальше каждое обновление платит за все индексы сразу.

Если у вас скачка не видно — посмотрите на долю HOT в первых двух
случаях. Если она и там низкая, значит новые версии строк не помещаются
на свою страницу; попробуйте `ALTER TABLE cost_t SET (fillfactor = 80)`
и пересоберите. Это тоже результат, и он про вашу нагрузку.

Число из последней строки — цена решения «добавим индекс на всякий
случай», выраженная в байтах WAL на каждое обновление. Её можно
предъявить в споре, где обычно предъявляют мнения.

## Что стоит проверить на своей базе

```sql
SELECT indexrelid::regclass FROM pg_index
WHERE NOT indisvalid OR NOT indisready;
```

Запрос из 12.6. Он никогда не должен возвращать строк. Если вернул —
это остаток прерванного `REINDEX CONCURRENTLY` или
`CREATE INDEX CONCURRENTLY`: место занимает, при вставках
поддерживается, при чтении не используется.
