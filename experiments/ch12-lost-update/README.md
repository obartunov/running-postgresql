# Стенд главы 12, часть 1: потерянное обновление

Вопрос: что происходит с **атомарностью**, когда чтение и запись
разнесены по границе приложения.

Это не тот стенд, который описывает сцена главы про пересечение
интервалов: тот проверяет, что предварительная проверка в приложении не
является инвариантом базы, и живёт в `../ch12-semantic-boundary`.
Здесь - более узкий и более частый случай: потерянное обновление.

```sh
createdb orm_bench
export PGDATABASE=orm_bench
./run.sh                     # все четыре режима
WORKERS=16 ITER=100 ./run.sh # сильнее конкуренция
```

Четыре режима одного и того же действия "прибавить единицу":

- `rmw` - `SELECT`, +1 в приложении, `UPDATE`. Так по умолчанию
  выглядит работа большинства ORM;
- `rmw-rr` - то же на `REPEATABLE READ` с повтором при отказе;
- `forupdate` - то же под `SELECT ... FOR UPDATE`;
- `sql` - `UPDATE ... SET balance = balance + 1`.

Ожидаемая сумма всегда `WORKERS * ITER`. Всё, что меньше, - потерянные
обновления, о которых база не сообщила: все транзакции завершились
успешно.

Измеренное - в `measured.md`.

## Чего стенд не делает

Не использует настоящий ORM. Воспроизводится шаблон доступа
"прочитал - посчитал - записал", а не конкретная библиотека: вывод
главы относится к шаблону, а не к названию фреймворка.
