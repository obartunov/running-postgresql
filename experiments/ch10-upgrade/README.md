# Эксперимент к главе 10: два числа, из которых состоит окно

Стенд не обновляет версию — для этого нужны два установленных релиза, и
это есть не у всех. Он меряет то, что определяет длину окна, и обе
величины измеряются на текущей версии.

## Проверки до окна

```sh
createdb upg_bench
export PGDATABASE=upg_bench
psql -f checks.sql
```

Пять запросов, которые выполняются на живой базе задолго до
обновления:

1. что вы когда-то трогали в конфигурации — список для разговора
   «зачем это здесь и верно ли до сих пор»;
2. расширения и доступные версии;
3. **расхождение версий правил сортировки** — если вторая выборка
   вернула строки, у вас уже сейчас есть индексы, отсортированные по
   устаревшим правилам;
4. расширенная статистика — она не переносится `pg_upgrade` даже в
   PG18, и её надо пересоздавать явно;
5. индексы по текстовым колонкам с размерами — список кандидатов на
   перестроение.

Пятый запрос стоит сохранить: это и есть смета работы, которая
свалится на вас при смене версии `glibc` или ICU.

## Два числа

```sh
./window-cost.sh
```

Скрипт создаёт данные, приводит базу в состояние «данные есть,
статистики нет» (то, в котором кластер оказывается после обновления на
версиях до PG18), и меряет:

- `vacuumdb --analyze-in-stages` — первая помощь, после которой
  планировщик перестаёт работать вслепую;
- полный `ANALYZE` — сколько до нормального состояния;
- `REINDEX CONCURRENTLY` текстовых индексов с их суммарным объёмом.

Третье число — самое полезное. Умножьте его на отношение объёма ваших
боевых текстовых индексов к объёму в стенде, и вы получите порядок
величины своей уязвимости к обновлению образа операционной системы.
Пока это число не измерено, план «обновим образ на выходных» ничем не
обеспечен.

## Если у вас есть две версии PostgreSQL

Тогда стоит сделать настоящую репетицию, и лучше — на кластере,
восстановленном учениями из главы 9:

```sh
/usr/lib/postgresql/18/bin/pg_upgrade \
  -b /usr/lib/postgresql/15/bin -B /usr/lib/postgresql/18/bin \
  -d /path/old -D /path/new --check
```

`--check` работает, пока старый кластер запущен, и находит большинство
несовместимостей заранее — это единственная часть обновления, которую
можно выполнить, ничего не останавливая.

Про режимы: копирование оставляет старый кластер рабочим,
`--link`/`--clone`/`--swap` — нет. После первого старта нового кластера
в быстром режиме старый запускать нельзя. Отдельный путь отката
(резервная копия или реплика) при быстром режиме обязателен.

## Что записать по итогам

Время самого обновления, вывод `--check`, список расширений,
потребовавших действий, время статистики и прогрева, наличие
расхождения сортировок и время перестроения, и полный список ручных
шагов в том порядке, в каком их придётся выполнять ночью.
