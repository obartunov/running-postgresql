# Измеренное: глава 12

Первый настоящий прогон стендов книги.

## Стенд

PostgreSQL 16.15 (Ubuntu 24.04, x86_64), контейнер.
`shared_buffers = 256MB`, `max_wal_size = 4GB`, **`fsync = off`**.

`fsync = off` влияет на время, но не на объём WAL и не на плотность
индекса — то есть на те величины, которые здесь измеряются. Времена из
этого прогона намеренно не приводятся: на такой конфигурации они
ничего не значат.

## 1. Раздувание индекса (`bloat.sh`)

Таблица 1 млн строк, индекс по колонке `status`, четыре раунда
обновлений этой колонки с `VACUUM` между ними.

| фаза | размер индекса | плотность листьев | фрагментация |
|---|---|---|---|
| после сборки | 6896 kB | 89.9 % | 0.0 |
| после обновлений и `VACUUM` | 13 MB | 61.6 % | 38.1 |
| после `REINDEX CONCURRENTLY` | 6912 kB | 89.7 % | 0.0 |

Индекс вырос вдвое при неизменном числе строк. `VACUUM` отработал —
и плотность осталась 61.6 %: место освобождено внутри страниц, но
страницы не слились. Это ровно тот механизм, о котором 12.4.

## 2. Цена индекса на обновлении (`index-cost.sh`)

500 тыс. строк, `fillfactor = 60`, 50 тыс. обновлений колонки `status`.

| вариант | WAL на строку | доля HOT |
|---|---|---|
| без индексов (кроме PK) | 145.7 Б | 68.1 % |
| 1 индекс по неизменяемой колонке | 170.9 Б | 68.1 % |
| 1 индекс по **изменяемой** колонке | 273.6 Б | 1.3 % |
| 4 индекса, один по изменяемой | 537.0 Б | 1.4 % |

Тот же прогон при `fillfactor = 80` и 100 тыс. обновлений:
228.2 / 284.6 / 323.8 / 616.4 Б, доля HOT 24.6 / 24.7 / 0.5 / 0.5 %.

Форма подтвердилась. Индекс по неизменяемой колонке добавляет около
17 % WAL и не трогает HOT. Индекс **по обновляемой** колонке роняет HOT
с 68 % до 1 % и добавляет ещё 60 % WAL — это скачок, а не приращение.
Дальше каждый следующий индекс платится полностью: с одного до четырёх
индексов WAL удваивается.

## 3. Что пошло не так с первого раза

Первый прогон был выполнен без `fillfactor`, то есть при значении по
умолчанию 100. Результат:

| вариант | WAL на строку | доля HOT |
|---|---|---|
| без индексов | 277.4 Б | 0.0 % |
| 1 индекс по неизменяемой | 351.9 Б | 0.0 % |
| 1 индекс по изменяемой | 350.9 Б | 0.0 % |
| 4 индекса | 639.0 Б | 0.0 % |

Доля HOT нулевая везде, и второй случай неотличим от третьего. Стенд
измерял не индексы, а переполненные страницы: на свежезагруженной
таблице без резерва места новая версия строки физически не помещается
рядом со старой, и HOT невозможен независимо от индексов.

Вывод занесён в сам стенд: `fillfactor` стал параметром со значением
по умолчанию 80, и в скрипте написано, почему.

Это, кстати, лучший аргумент за то, чтобы гонять стенды, а не
описывать ожидаемую форму результата. Ожидание было правильным, а
измерял стенд не то.
