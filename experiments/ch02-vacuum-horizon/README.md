# Эксперимент к главе 2: у кого VACUUM отбирает право работать

Одна и та же нагрузка, три сценария, различающиеся только тем, кто в
это время держит снимок данных.

## Предварительно

```sh
createdb vac_bench
export PGDATABASE=vac_bench
psql -c "ALTER SYSTEM SET max_prepared_transactions = 10"   # нужно для C
pg_ctl restart -D $PGDATA                                   # параметр требует рестарта
```

`max_prepared_transactions = 0` по умолчанию. Если он остался нулём,
сценарий C просто не запустится - и это, кстати, лучшая защита от
описанного в главе инцидента на реальном сервере.

## Прогоны

```sh
./scenario.sh A     # никто не мешает
./scenario.sh B     # открытая REPEATABLE READ транзакция
./scenario.sh C     # брошенная PREPARE TRANSACTION
```

Каждый прогон делает `ROUNDS` (по умолчанию 5) циклов
"обновить пятую часть таблицы -> `VACUUM VERBOSE` -> замерить".

## Что смотреть

**Размер.** `results/*/size.txt`. В A размер после первого цикла
стабилизируется. В B и C растёт примерно линейно от цикла к циклу.
Отношение конечных размеров B/A - амплификация пространства, вызванная
одним удерживаемым снимком.

**Право на работу.** В `results/*/vacuum-N.txt`:

```
tuples: N removed, M remain, K are dead but not yet removable
oldest xmin: ...
```

В A растёт `removed`. В B и C `removed` близко к нулю, а `K` растёт от
цикла к циклу. Это и есть определение бесполезной работы: VACUUM
прочитал всю таблицу и не освободил ничего.

**Кто виноват.** `results/*/horizon.txt`. В B виновник виден в разделе
1 (`pg_stat_activity`). В C разделы 1-3 пусты, а виновник - в разделе 4.
Ради этого контраста сценарий C и существует.

**Возраст горизонта.** `age(backend_xmin)` / `age(transaction)` растёт
монотонно в B и C. Это та величина, на которую в проде вешается алерт,
а не `n_dead_tup`.

## Аккуратность

- `autovacuum_enabled = off` ставится на таблицу в `setup.sql`
  намеренно: иначе фоновый воркер вклинивается между шагами и результат
  перестаёт быть повторяемым. В проде так делать нельзя.
- Сценарий C оставляет подготовленную транзакцию до конца прогона и
  откатывает её в `trap EXIT`. Если вы прервали скрипт жёстко,
  проверьте `SELECT * FROM pg_prepared_xacts` и откатите руками:
  `ROLLBACK PREPARED 'ch02_orphan';`
- База выбрасываемая. Ничего из этого не выполняется на сервере,
  который кому-то нужен.

## Что дописать к результатам руками

Версия сервера, `shared_buffers`, файловая система, было ли на машине
что-то ещё. Как и в главе 1, без этого цифры нельзя сравнивать между
стендами.
