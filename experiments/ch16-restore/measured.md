```text
Experiment:   restore-drill
Chapter:      глава 16 (backup/restore) и глава 14 (готовность после
              старта) основной рукописи
PostgreSQL:   16.15 (Ubuntu), commit not recorded
Machine/OS:   см. ../ENVIRONMENT.md
Date:         2026-09-06
Question:     из каких участков состоит время восстановления и в какой
              момент база считается восстановленной
Result:       сервер отвечает через 0.62 s, восстановление
              заканчивается на 3.82 s; неатомарный archive_command
              рвёт архив
Scripts:      drill.sh
Raw output:   results/ (не версионируется)
```

Стенд: отдельный кластер, `pgbench` scale 20 (копия 338 MB), после
снятия копии 20 секунд нагрузки, затем остановка `pg_ctl -m immediate`
и восстановление из копии с проигрыванием архива.

## Часть 1. Участки восстановления

### Observed

| участок | время |
|---|---|
| снятие базовой копии | 1.98 s |
| развёртывание (`cp -a` каталога) | 0.96 s |
| от `pg_ctl start` до первого успешного ответа | **0.62 s** |
| от `pg_ctl start` до конца проигрывания | **3.82 s** |
| первый запрос по холодному кэшу | 0.96 s |
| тот же запрос повторно | 0.55 s |

WAL, произведённый после копии: 295 MB.

**Точные определения точек измерения.**

*First response* - момент, когда цикл
`psql -c "SELECT 1"` впервые завершился с нулевым кодом возврата.
Опрос шёл с интервалом 0.2 s, поэтому величина имеет соответствующую
дискретность.

*Replay finished* - момент, когда
`psql -Atc "SELECT pg_is_in_recovery()"` впервые вернул `f`. Опрос шёл
с интервалом 0.5 s. Восстановление выполнялось с `recovery.signal` без
заданного `recovery_target`, то есть заканчивалось концом доступного
архива с последующим promote.

Обе точки берутся от одного и того же `T4` - вызова `pg_ctl start`.

### Derived

Отношение: 3.82 / 0.62 ≈ **6.2×**. То есть в течение примерно 3.2
секунд сервер отвечал на запросы, не закончив восстановление.

### Interpretation

Сервер принимает соединения при достижении согласованности, а не по
завершении проигрывания. Всё это время база отдаёт данные на момент
копии. Готовность после восстановления определяется
`pg_is_in_recovery() = false`, а не успешным подключением.

### Замечание о валидности

Первая версия стенда считала восстановление законченным по первому
успешному `SELECT 1` и записывала в RTO 0.63 s вместо 3.82 s.
Это та же ошибка, которую делает дежурный, докладывающий "поднялись"
по первому ответу `psql`.

## Часть 2. Неатомарный `archive_command`

### Observed

При `archive_command = 'test ! -f $ARCHIVE/%f && cp %p $ARCHIVE/%f'`
восстановление остановилось:

```text
FATAL:  archive file "000000010000000000000024" has wrong size:
        851968 instead of 16777216
```

**Точный сценарий.** Кластер работал под нагрузкой `pgbench`,
архивирование шло указанной командой. Кластер был остановлен
`pg_ctl -m immediate` (моделирование аварии) в момент, когда
копирование очередного сегмента не завершилось. В каталоге архива
остался файл размером 851 968 байт вместо 16 777 216. Проигрывание
дошло до него и завершилось с `FATAL`.

Отдельно: ситуация возникла **не** специально. Она была получена при
первом же прогоне после исправления определения готовности.

### Derived

Ничего не выводится: это единичное наблюдение отказа, а не измерение.

### Interpretation

`cp` не атомарен. Авария сервера в момент архивирования порождает
дыру в архиве, которая не обнаруживается до попытки восстановления.
`archive_command` должна писать во временное имя и переименовывать;
`mv` в пределах файловой системы атомарен. В стенде команда исправлена.

## Часть 3. Незапланированное: восстановление после аварии контейнера

Между прогонами других стендов контейнер с основным сервером был убит
без остановки PostgreSQL.

### Observed

```text
LOG: database system was interrupted; last known up at 05:47:08 UTC
LOG: database system was not properly shut down; automatic recovery in progress
LOG: checkpoint complete: ... distance=3300353 kB
LOG: database system is ready to accept connections   (07:06:57)
```

Старт был инициирован в 07:04:27. `pg_ctl start` со стандартным
ожиданием 60 s сообщил "server did not start in time".

### Derived

Проигрывание около 3.3 GB WAL заняло примерно 150 s, то есть порядка
**20 MB/s** на этой машине. Значение грубое: точный момент начала
redo из лога не выписывался.

### Interpretation

Инструмент запуска сообщил о неудаче раньше, чем сервер поднялся.
Ожидание восстановления измеряется логом сервера, а не таймаутом
`pg_ctl`.
