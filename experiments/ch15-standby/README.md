# Эксперимент к главе 7: один конфликт, три способа проиграть

Поднимает primary и реплику на одной машине, на портах 55432 и 55433,
и воспроизводит конфликт восстановления целиком. Ничего в вашей
основной установке не трогается: всё живёт в `/tmp/ch07`.

```sh
./make-cluster.sh          # поднять пару
./conflict.sh 1            # max_standby_streaming_delay = 0
./conflict.sh 2            # max_standby_streaming_delay = 30s
./conflict.sh 3            # hot_standby_feedback = on
./make-cluster.sh clean    # удалить всё
```

Нужны `initdb`, `pg_basebackup`, `pg_ctl` в PATH - то есть обычная
локальная установка PostgreSQL. Автовакуум на `pgbench_accounts`
отключён намеренно: момент очистки задаётся вручную, иначе прогоны не
повторяются.

## Что происходит в каждом прогоне

На реплике стартует транзакция `REPEATABLE READ`, которая читает
таблицу и держит снимок двадцать секунд. На primary в это время идут
`UPDATE` и `VACUUM`: очистка освобождает те версии строк, которые
снимок на реплике ещё видит.

**Прогон 1.** Реплика не готова ждать. В `results/run1/`:

- `standby-query.txt` - `canceling statement due to conflict with
  recovery`;
- `conflicts.txt` - `confl_snapshot` увеличился;
- `replication.txt` - `replay_lag` близок к нулю.

Реплика свежая, запрос мёртв.

**Прогон 2.** Реплика готова ждать до тридцати секунд. Запрос
доживает. Смотрите `replay_lag` в `replication.txt` - это и есть цена,
выраженная в свежести. Если запрос длиннее задержки, его всё равно
отменят: тридцать секунд - это не "навсегда".

**Прогон 3 - главный.** Реплика сообщает primary, что ей нужны старые
версии строк. Запрос выживает при любой длительности, `replay_lag`
маленький, конфликтов нет. Всё хорошо - на реплике.

Теперь смотрите не туда: `results/run3/primary-vacuum.txt`.

```
tuples: 0 removed, ... are dead but not yet removable
oldest xmin: ...
```

`VACUUM` на primary отработал и не смог ничего освободить. Это та же
строка, вокруг которой построена глава 2, и держатель горизонта сидит
на другой машине. В `replication.txt` он виден по `backend_xmin`.

## Что стоит попробовать сверх сценариев

Замените в третьем прогоне `pg_sleep(20)` на `pg_sleep(300)` и
посмотрите на размер `pgbench_accounts` на primary до и после.
Пятиминутный отчёт на реплике - пятиминутное удержание горизонта на
primary.

Второй вариант: вместо `UPDATE`+`VACUUM` выполните на primary
`ALTER TABLE pgbench_accounts ADD COLUMN x int`. Конфликт будет уже не
снимка, а блокировки (`confl_lock`), и это прямая связь с главой 3.
