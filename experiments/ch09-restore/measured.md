# Измеренное: глава 9 — незапланированное

Полные учения (`drill.sh`) ещё не проводились. Но во время прогонов
других стендов контейнер с сервером был убит без остановки PostgreSQL,
и восстановление после аварии измерилось само.

PostgreSQL 16.15, контейнер, `shared_buffers = 256MB`, `fsync = off`.

```
LOG: database system was interrupted; last known up at 05:47:08 UTC
LOG: database system was not properly shut down; automatic recovery in progress
...
LOG: checkpoint complete: ... distance=3300353 kB
LOG: database system is ready to accept connections   (07:06:57)
```

Проигрывание около **3.3 ГБ WAL заняло примерно 150 секунд** — порядка
20 МБ/с на этой машине. `pg_ctl start` со стандартным ожиданием в
60 секунд успел отчитаться «server did not start in time» задолго до
того, как сервер поднялся.

Два наблюдения для главы, оба незапланированные.

Первое: это и есть то самое число, к которому глава 1 отсылала за
`max_wal_size`, а глава 9 назвала суммой чужих решений. Здесь
`max_wal_size = 4GB`, и восстановление честно проиграло почти весь этот
объём.

Второе, практическое: инструмент запуска сказал «не стартовал» раньше,
чем сервер стартовал. Дежурный, который в этот момент решит, что
кластер сломан, и начнёт что-то предпринимать, сделает хуже. Ожидание
восстановления надо мерить логом сервера, а не таймаутом `pg_ctl`.

# Измеренное: учения (`drill.sh`)

PostgreSQL 16.15, контейнер, `pgbench` scale 20 (копия 338 МБ),
295 МБ WAL после копии.

| участок | время |
|---|---|
| снятие копии | 1.98 с |
| развёртывание | 0.96 с |
| **старт до первого ответа сервера** | **0.62 с** |
| **до конца проигрывания** | **3.82 с** |
| первый запрос (холодный кэш) | 0.96 с |
| тот же запрос (прогретый) | 0.55 с |

## Первый вывод: «база отвечает» не значит «восстановление закончено»

Сервер начал принимать соединения через 0.62 секунды, а проигрывание
закончилось на 3.82 — в шесть раз позже. Всё это время база отвечает и
отдаёт данные **на момент копии**, без изменений, сделанных после неё.

Прежняя версия стенда считала восстановление законченным по первому
успешному `SELECT 1` и записывала в RTO 0.63 секунды вместо 3.8. Это та
же ошибка, которую сделает дежурный, доложив «поднялись», как только
`psql` подключился.

Ждать надо `pg_is_in_recovery() = false`. Мерить надо оба числа: между
ними живёт неполная база, которая выглядит рабочей.

## Второй вывод: `cp` в архив — не атомарная операция

Первый прогон после починки упал:

```
FATAL: archive file "000000010000000000000024" has wrong size:
       851968 instead of 16777216
```

Сервер был остановлен в режиме `immediate` посреди копирования сегмента
в архив, и в архиве остался обрезанный файл. Восстановление дошло до
него и остановилось — та самая стена из главы, полученная не в
рассуждении, а на стенде.

`archive_command` в стенде исправлена на запись во временное имя с
последующим `mv`. Это же требование относится к любому боевому
`archive_command`: копирование должно быть атомарным, иначе авария на
primary порождает дыру в архиве.
