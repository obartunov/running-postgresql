# Стенд главы 12: граница семантики

Вопрос главы: защищает ли проверка в приложении инвариант, о котором
база не знает.

```sh
createdb sem_bench
export PGDATABASE=sem_bench
./run.sh                      # шесть воркеров, девять попыток каждый
WORKERS=12 ITER=20 ./run.sh   # сильнее конкуренция
```

Одна и та же задача - не бронировать ресурс на пересекающиеся
интервалы - решается двумя способами: проверкой в приложении и
ограничением `EXCLUDE USING gist` в базе. Шаблон доступа в обоих
случаях одинаковый: проверить, затем вставить.

Смотреть надо на последнюю колонку - число пересекающихся пар после
прогона. У таблицы без ограничения оно ненулевое при нуле ошибок: база
не сообщала ни о чём, потому что правила не знала.

Соседний стенд `../ch12-lost-update/` показывает второй механизм той же
границы - потерю обновления при read-modify-write.

## Почему именно интервалы

Пример выбран не ради экзотики. Ограничение исключения опирается на
тип-диапазон, оператор пересечения и метод доступа GiST - то есть на
расширяемость PostgreSQL, а не на общий для всех СУБД `UNIQUE`. Такой
инвариант в приложении обычно и оказывается: выразить его в базе
кажется сложнее, чем написать проверку.
