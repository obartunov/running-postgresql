# Измеренное: глава 9 — незапланированное

Полные учения (`drill.sh`) ещё не проводились. Но во время прогонов
других стендов контейнер с сервером был убит без остановки PostgreSQL,
и восстановление после аварии измерилось само.

PostgreSQL 16.15, контейнер, `shared_buffers = 256MB`, `fsync = off`.

```
LOG: database system was interrupted; last known up at 05:47:08 UTC
LOG: database system was not properly shut down; automatic recovery in progress
...
LOG: checkpoint complete: ... distance=3300353 kB
LOG: database system is ready to accept connections   (07:06:57)
```

Проигрывание около **3.3 ГБ WAL заняло примерно 150 секунд** — порядка
20 МБ/с на этой машине. `pg_ctl start` со стандартным ожиданием в
60 секунд успел отчитаться «server did not start in time» задолго до
того, как сервер поднялся.

Два наблюдения для главы, оба незапланированные.

Первое: это и есть то самое число, к которому глава 1 отсылала за
`max_wal_size`, а глава 9 назвала суммой чужих решений. Здесь
`max_wal_size = 4GB`, и восстановление честно проиграло почти весь этот
объём.

Второе, практическое: инструмент запуска сказал «не стартовал» раньше,
чем сервер стартовал. Дежурный, который в этот момент решит, что
кластер сломан, и начнёт что-то предпринимать, сделает хуже. Ожидание
восстановления надо мерить логом сервера, а не таймаутом `pg_ctl`.
