# Учения к главе 9: измерьте свой RTO по участкам

Полный цикл на одной машине: кластер, базовая копия, архив WAL,
нагрузка, авария, восстановление — с секундомером на каждом участке.
Всё живёт в `/tmp/ch09`, основную установку не трогает.

```sh
./drill.sh          # немного WAL после копии
./drill.sh heavy    # много WAL после копии
./drill.sh clean    # удалить всё
```

Нужны `initdb`, `pg_basebackup`, `pg_ctl`, `pgbench` в PATH.

## Что печатается

Пять чисел: снятие копии, развёртывание, старт и проигрывание, первый
запрос по холодному кэшу и тот же запрос по прогретому. Плюс RTO как
сумма тех участков, которые в реальной аварии считаются простоем.

## Два наблюдения, ради которых это написано

**Доля участков.** На ноутбуке передачи практически нет — копия
рядом, — и доминировать будет проигрывание WAL. В проде с копией в
объектном хранилище доминирует передача, и обычно с большим отрывом.
Оптимизировать надо тот участок, который главный **у вас**, а не тот, о
котором чаще пишут.

**Цена редких копий.** Сравните `results/drill-light.txt` и
`results/drill-heavy.txt`. Разница во времени проигрывания при одной и
той же копии — это минуты простоя, купленные тем, что копия снимается
реже. Она же — цена решения из главы 1: чем больше `max_wal_size` и
чем реже чекпойнты, тем дольше проигрывание.

Разница между холодным и тёплым запросом — участок, который в отчёты
об инцидентах обычно не попадает, хотя в реальном RTO присутствует
всегда.

## Что стоит попробовать сверх сценария

**Восстановление на точку во времени.** Запомните время в середине
нагрузки и добавьте в `postgresql.conf` восстановленного кластера:

```
recovery_target_time = '...'
recovery_target_action = 'promote'
```

Затем проверьте, что данных после этой точки в базе нет. Это тот самый
PITR, ради которого ведётся архив.

**Разрыв архива.** Удалите один сегмент из `/tmp/ch09/archive` и
повторите восстановление. Проигрывание остановится на разрыве —
буквально стена из главы 9. Посмотрите, что при этом пишет
`restored.log`.

**Проверка целостности.** На восстановленном кластере запустите
`pg_amcheck` (PG14+). На боевой машине такая проверка стоит дорого, на
восстановленной — ничего, и это лучшее применение учебному кластеру.

## Оговорка о масштабе

Стенд меряет структуру RTO, а не его величину. Ваши абсолютные числа в
проде будут другими на порядки, и получить их можно только учениями на
настоящем объёме и настоящем канале. Смысл стенда — научиться считать
по участкам и увидеть, какой из них доминирует.
